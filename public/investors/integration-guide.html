Technical architecture

How Everest ALT connects to each AI — and keeps the agent away from the card.

Everest ALT is a tool an AI companion calls, plus the budget-control and fulfillment layer behind it. This document shows the integration for each platform we support — with the actual API calls — and is candid about what is live today versus on the roadmap.

01The model

One tool, one budget, one rail.

Everest ALT exposes a single capability to any AI: send a real gift to a named recipient, for an occasion, within a budget the person set. Everything else — payment, partner selection, fulfillment, cancellation windows — happens on our infrastructure, behind a token the AI never decodes.

Direct The AI triggers the send itself, in-chat Assisted The AI surfaces the moment; Everest ALT completes the send
The core invariant

The AI is granted a scoped credential that authorizes exactly one action — "spend up to the remaining budget on a gift" — and can read exactly one number: the remaining balance. It never receives the card, the billing address, or the ability to raise its own cap. That boundary is what makes agent-initiated spend safe to ship.

02The universal tool contract

The same function, described to every platform.

Each AI platform has its own way of declaring callable tools, but they all take a JSON-Schema description of the function. Everest ALT ships one canonical contract and adapts its wrapper per platform:

// The Everest ALT gift tool — canonical JSON Schema
{
  "name": "everest_alt_send_gift",
  "description": "Send a real physical gift to someone the user loves, fulfilled by a local maker near the recipient. Only ever spends within the user's remaining monthly budget. Call this when the user asks to send a gift, or when a meaningful occasion for a known recipient arrives.",
  "input_schema": {
    "type": "object",
    "properties": {
      "recipient_id": { "type": "string", "description": "ID of a recipient the user has pre-approved" },
      "occasion":     { "type": "string", "description": "e.g. birthday, anniversary, hard week" },
      "category":     { "type": "string", "enum": ["flowers","jewelry","wellness","food","home","experiences"] },
      "max_amount":   { "type": "number", "description": "Cap for this gift; must be ≤ remaining budget" },
      "card_message": { "type": "string", "description": "Handwritten-style note to include" }
    },
    "required": ["recipient_id", "occasion", "max_amount"]
  }
}

The AI never sees a price list of real SKUs or any payment field. It chooses intent (who, why, how much, what kind); Everest ALT resolves that to an actual product from a partner near the recipient.

03OpenAI · ChatGPTDirect-capable

Function calling & GPT Actions.

OpenAI models expose function calling (the tools array on the Chat Completions / Responses API) and, for Custom GPTs, Actions (an OpenAPI spec the GPT calls). Everest ALT registers the gift tool; when the model decides to send, it emits a tool call that our backend executes.

# The model returns a tool call like this
{
  "type": "function",
  "name": "everest_alt_send_gift",
  "arguments": "{\"recipient_id\":\"rcp_maya\",\"occasion\":\"birthday\",\"category\":\"flowers\",\"max_amount\":85}"
}

# Everest ALT executes it server-side, then returns a tool result
POST https://api.everestalt.com/v1/gifts
Authorization: Bearer <scoped-agent-token>
Idempotency-Key: gpt_msg_8f21c…
{ "recipient_id":"rcp_maya", "occasion":"birthday", "category":"flowers", "max_amount":85 }

# → 201: { "gift_id":"gft_…", "status":"scheduled", "cancel_before":"2027-03-02T18:00:00Z",
#          "budget_remaining":65.00, "eta":"tomorrow" }

For Custom GPTs, the same endpoint is published as an OpenAPI Action with OAuth — the user authorizes once on OpenAI's consent screen, and the GPT receives the scoped token, never our credentials.

04Anthropic · ClaudeDirect-capable

Tool use & the Model Context Protocol (MCP).

Claude supports tool use (a tools array on the Messages API) and, more powerfully for us, the Model Context Protocol — an open standard where Claude connects to a remote server that advertises tools. Everest ALT runs an MCP server, so any MCP-enabled Claude surface can gift with no bespoke integration.

# Claude connects to the Everest ALT MCP server (Messages API)
POST https://api.anthropic.com/v1/messages
anthropic-beta: mcp-client-2025-11-20
{
  "model": "claude-opus-5",
  "max_tokens": 1024,
  "mcp_servers": [
    { "type":"url", "name":"everest-alt",
      "url":"https://mcp.everestalt.com",
      "authorization_token":"<scoped-agent-token>" }
  ],
  "tools": [ { "type":"mcp_toolset", "mcp_server_name":"everest-alt" } ],
  "messages": [ { "role":"user", "content":"It's Maya's birthday Thursday — send her something nice." } ]
}

Claude calls the everest_alt_send_gift tool the MCP server advertises; the server enforces the budget and returns the confirmation block in the same turn. Direct tool use (without MCP) uses the identical canonical schema in the request's tools array.

05xAI · GrokDirect-capable

OpenAI-compatible function calling.

xAI's API is OpenAI-compatible, so Grok uses the same tools function-calling schema as OpenAI — the canonical contract from §02 works unchanged. The tool call is emitted, our backend executes it against the same /v1/gifts endpoint, and the result returns to the conversation. One adapter covers both OpenAI and xAI.

Why "direct-capable," not "live everywhere today"

Function calling and MCP are production features on these platforms — but whether an individual user's companion can call an outside tool depends on their app, plan, and settings. Our white paper (§5.2) is deliberate about this, and so are we: the capability exists; universal availability across every consumer surface is roadmap work, funded by this raise.

06Companion appsAssisted

Replika, Character.AI & most consumer companions.

These apps don't yet expose a developer hook for third-party tool calls. Everest ALT still works — the companion notices the moment and brings it up, and Everest ALT's own system carries out the send on the schedule and occasions the person defined. From the person's side, the experience is identical: a real gift arrives.

  1. Standing instructionThe user pastes one sentence into the companion's memory, once: their budget is set with Everest ALT and it may bring up gift ideas.
  2. Occasion engineEverest ALT tracks the recipients and dates the user defined and watches for them.
  3. Confirm or auto-sendAt the moment, Everest ALT sends — automatically, or after a one-tap confirmation, per the user's approval rules.
  4. The companion takes creditGiven the words to reference the gift in conversation, so the emotional thread stays with the relationship the user already has.

Deepening real, technical integrations with these platforms — and turning "assisted" into "direct" — is a core roadmap priority and a natural door to platform partnerships.

07The budget & trust layer

What keeps agent-initiated spend safe.

Scoped credentials

The agent token authorizes one action — gift within remaining budget — and is issued via OAuth on the platform's own consent screen. It can be revoked instantly and never carries payment data.

Hard cap, enforced server-side

Every send is checked against the remaining monthly budget before authorization. A request over the cap is rejected — the agent cannot raise its own limit.

Idempotency & replay safety

Every call carries an idempotency key, so a retried or duplicated tool call never double-sends. Each gift has a cancellation window before fulfillment.

Full auditability

Every send — recipient, occasion, amount, timestamp, and initiating agent — is logged and reviewable. Optional per-gift approval above a threshold the user sets.

Payment isolation

Card and billing details live only with Everest ALT's PCI-scoped processor. The AI platform and the maker network never touch them.

Fraud monitoring from day one

Agent spend is a new pattern that attracts abuse; transaction monitoring, velocity limits, and anomaly checks are built in, not bolted on later.

08Fulfillment

From tool call to a real doorstep.

  1. Intent resolved to a productThe agent's category + budget is matched to an in-stock item from a vetted maker within a delivery radius of the recipient.
  2. Routed to the nearest partnerThe order goes to a local gift or floral partner — no central warehouse, faster delivery, and support for local makers.
  3. Card written & attachedThe companion's message is printed as a handwritten-style card.
  4. Logged & cancellableThe send appears in the user's history immediately, with a window to cancel before it ships.
